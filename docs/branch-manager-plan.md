# 총괄매니저 — 설계안 (구현 전, 대표 승인 대기)

**조사만 했다. 코드는 한 줄도 고치지 않았다.** main 은 `cc79d7c` 에서 동결 중이다.

읽은 자리: `firestore.foundation.rules` 전체(1,597줄), `src/data/repositories/*`,
`src/App.jsx` 의 역할 게이트, `functions/src/*`, `firestore.foundation.indexes.json`.
**프로덕션은 읽지 못한다** — 2번의 "지금 비어 있는 문서 수" 는 대표가 눌러야
나오는 숫자이고, 그것을 세는 방법을 아래에 적었다.

서열: FC매니저(`manager`) < 총괄매니저(새 역할) < 대표(`owner`).

---

## 먼저 — 설계를 시작하기 전에 결정해야 하는 것 넷

이 넷은 내가 고를 수 없다. 답에 따라 작업 크기가 두 배씩 달라진다.

### ① 이름이 이미 쓰이고 있다

`branch_manager` 는 **이미 있다.** 단, 역할이 아니라 **직함(title)** 이고
우리말로 "점장" 이다 (`functions/shared/constants.mjs:47`). 급여 규칙도 그
직함을 본다 — 점장·팀장 1:1 재등록(이벤트) 31,000 (`deduction-pricing.mjs`).

총괄매니저를 `role: "branch_manager"` 로 만들면 **같은 글자가 두 뜻**이 된다.
제안: 역할 값은 `area_manager`, 화면 문구는 "총괄매니저". 직함 쪽은 손대지
않는다.

### ② "다른 지점은 목록에도 안 보이게 서버에서 막는다" 는 지금 **아무 역할에게도** 안 되어 있다

지금 회원 목록과 회원권 목록은 **컬렉션을 통째로 받아 기기에서 거른다.**

| 읽는 곳 | 질의 | 지점 조건 |
| --- | --- | --- |
| `listClients` (`client-repository.js:55`) | `collection(orgs/{org}/clients)` — 조건 없음* | 받은 뒤 기기에서 (`:161`) |
| `listPasses` (`pass-repository.js:197`) | 컬렉션 통째 | 없음 (회원으로만 거름 `:209`) |
| `listLocations` · `listProducts` | 컬렉션 통째 | 없음 |
| 급여 (`payroll-repository.js:99`) | collectionGroup + organizationId | 받은 뒤 지점별로 묶음 (`:395`) |

\* 강사일 때만 `where("instructorIds","array-contains",uid)` 가 붙는다 — 그것도
규칙 3단계가 **아직 배포되지 않아** 지금은 앱의 선의일 뿐이다.

그래서 "서버에서 막는다" 는 **새로 만드는 일**이지 "역할 하나 추가" 가 아니다.
이것이 이 작업의 크기 대부분이다.

### ③ 상품 "수정·삭제" 는 지금 존재하지 않는다

규칙이 상품을 **status 한 칸만** 바꾸게 열어 두었고
(`firestore.foundation.rules:550`), **delete 는 false** 다 (`:561`).

> 이미 발급된 회원권이 그 상품의 조건을 가리키고 있어서, 고치는 대신 보관하고
> 새로 만든다 (`:487` 머리말)

"상품 추가·수정·삭제" 를 그대로 받으면 **총괄매니저와 무관한 설계 변경**이
하나 끼어든다. 두 갈래:

- **(가)** 지금 모양 유지 — 총괄매니저도 추가·보관만. 문구는 "수정 대신 새로
  만들기", 삭제는 "종료"
- **(나)** 진짜 수정·삭제를 연다 — 이미 발급된 회원권이 무엇을 가리키게 할지
  부터 정해야 한다. **이것은 따로 낸다.**

**(가)를 권한다.** 총괄매니저 작업에 섞으면 둘 다 늦어진다.

### ④ 지점이 접근 경계가 되는 순간, **지점 값 자체가 문이 된다**

지금 회원의 `locationId` 는 **강사 포함 누구나 바꿀 수 있다**
(`firestore.foundation.rules:415` — update 의 `immutable` 목록에 없다).

지점으로 막기 시작하면 이 한 줄이 곧 "남의 지점 회원을 내 지점으로 끌어오는
버튼" 이 된다. `instructorIds` 를 앱 쓰기에서 막아 둔 것과 **똑같은 이유**다
(`:388` 주석).

→ 회원의 지점 변경은 **callable 하나로만**. 규칙에서는 `immutable` 로 잠근다.

### 2-2. 세 가지를 꼭 손봐야 한다

1. **`instructorClientTotals` 에 `locationId` 를 넣으려면 규칙 배포가 먼저다.**
   `hasOnly` 가 닫힌 목록이라 필드를 하나 늘리는 순간 **모든 차감이 거부된다**
   (`:583`). 규칙 → 앱 순서를 거꾸로 하면 센터 전체가 수업 확정을 못 한다.
   *단, 이 컬렉션은 지점으로 거를 이유가 약하다 — 아래 2-4 참고.*
2. **`ledger.locationId` 는 아무도 검증하지 않는다.** 규칙이 존재만 요구하고
   회원권과 대조하지 않는다. 지금은 매출이 엉뚱한 지점에 찍히는 정도지만,
   지점이 **급여의 경계**가 되면 그만큼이 아니다. `getAfter(pass)` 의
   `locationId` 와 대조하는 조건을 한 줄 넣는다 — `instructorId` 를 회원권과
   대조하는 조건 바로 옆이다.
3. **`clients.locationId` 가 null 을 허용한다.** 지점으로 거르면 null 인 회원은
   **누구에게도 안 보인다.** 대표에게만 "지점 없는 회원 N명" 으로 보이게 하고,
   그 수가 0 이 되기 전에는 규칙을 켜지 않는다 — `instructorIds` 의
   "담당 없는 회원 34명" 과 **같은 모양의 보류 조건**이다.

### 2-3. 비어 있는 문서 수를 세는 법 — **대표가 눌러야 나온다**

내가 프로덕션을 읽을 수 없다. `verifyInstructorIds`
(`functions/src/index.js:660`) 와 같은 모양의 **읽기 전용 owner callable** 을
하나 만든다. 이름·연락처는 세지 않고 건수만 돌려준다 (§7).

```
locationCoverage(organizationId) →
  clients         { total, withLocation, missing, unknownLocationId }
  passes          { total, missing }
  ledger          { total, missing, mismatchedWithPass }
  lessons         { total, missing }
  lessonNotes     { total }          ← 필드 자체가 없다
  memberships     { total, withLocation, missing }
```

`unknownLocationId` 는 **있는데 `locations` 에 없는 id** 다. 비어 있는 것보다
이쪽이 위험하다 — 값이 있으니 검사를 통과하고, 그 회원은 어느 지점 목록에도
안 뜬다.

| 컬렉션 | 채우는 법 | 비고 |
| --- | --- | --- |
| `clients` | 대표 화면에서 지점 없는 회원을 보고 손으로 지정. 회원권이 있으면 **가장 최근 회원권의 지점**을 제안 | 제안이지 자동이 아니다. 지점 이동 회원이 섞인다 (4번) |

## 3. 규칙에서 "총괄매니저 + 그 지점" 을 판정하는 법

### 3-1. 판정 함수

`memberships` 문서에 `locationIds` (문자열 배열) 를 둔다. 규칙은 이미
`membership(organizationId)` 로 그 문서를 읽고 있다 (`:13`).

```
function areaManagerLocations(organizationId) {
  return isActiveMember(organizationId)
    && membership(organizationId).data.role == "area_manager"
    ? membership(organizationId).data.get("locationIds", [])
    : [];
}

function managesLocation(organizationId, locationId) {
  return locationId in areaManagerLocations(organizationId);
}
```

**비용에 주의한다.** `membership()` 은 `get()` 이고 규칙의 `get` 은 요청당
10회(단일) · 20회(배치) 가 상한이다. 지금 `hasRole` 하나에 이미 두 번
(`exists` + `get`) 들어가고, 한 조건에서 `hasRole` 을 여러 번 부르면 금방
닿는다. **역할 판정은 요청당 한 번만** 부르도록 조건을 묶어 쓴다.

### 3-2. get 과 list 는 다르게 막힌다 — 이 파일이 이미 겪은 일이다

규칙 머리말(`:109~145`)에 적혀 있다.

> `resource.data` 를 보는 **list** 규칙은 질의가 그 필드를 제약하지 않으면
> 만족시킬 수 없다. Firestore 는 false 를 주지 않고 **질의 전체를 거부**하고,
> 그것은 화면에 **빈 목록**으로 도착한다. 컬렉션이 비어 있으면 조용히 통과해서
> 첫 문서가 생기기 전까지 결함이 안 보인다.

그래서 지점 판정은 **두 벌**이 필요하다.

| | get | list |
| --- | --- | --- |
| 조건 | `managesLocation(org, resource.data.locationId)` | 질의가 `where("locationId","in",[...])` 를 **증명해야** 한다 |
| 질의가 안 좁히면 | 그 문서만 거부 | **화면 전체가 빈다** |

규칙만으로 "질의가 좁혔는가" 를 확인하는 길은 없다 — 규칙은 질의를 못 본다.
할 수 있는 것은 `resource.data.locationId` 를 보는 조건을 **list 에 그대로
두는 것**뿐이고, 그러면 안 좁힌 질의는 거부된다. 그것이 강제 장치다.

`in` 은 **최대 30개**다. 한 사람이 맡는 지점이 30개를 넘을 일은 없지만,
넘으면 질의가 조용히 실패하므로 지정 화면에서 막는다.

### 3-3. 화면 목록 질의를 바꿔야 하는 범위

| 읽는 곳 | 지금 | 바꿀 것 | 새 색인 |
| --- | --- | --- | --- |
| `listClients` | 조건 없음 | `where("locationId","in",myLocations)` | 단일 필드 — 자동 |
| `listPasses` | 조건 없음 | 같음 | 자동 |
| 회원 상세의 회원권 | `listPasses` 재사용 | 따라옴 | — |
| 급여 (`loadOrganizationMonthlyPayroll`) | org + type + occurredAt | + `locationId in` | **필요** (ledger 그룹) |
| 발급 내역 (`issue-report`) | org + type + occurredAt | + `locationId in` | **필요** |
| 잔여 점검 (`listLedgerByOrganization`) | org + occurredAt | + `locationId in` | **필요** |
| 강사 목록 (`listMemberships`) | org | + 지점 교집합은 **기기에서** | 배열 대 배열은 질의로 못 한다 |
| `lessonNotes` · `lessons` | 조건 없음 | 지점 필드부터 (2-4) | |
| 변화기록 계열 8개 | 조건 없음 | **이번 묶음 밖** (6번) | |

**강사 목록이 질의로 안 되는 이유:** 내 `locationIds` 도 배열이고 강사의
`locationIds` 도 배열이다. Firestore 에 "배열 대 배열 교집합" 질의가 없다.
→ 소속은 조직 단위로 읽고 **규칙은 열어 둔 채** 화면에서 거른다. 소속 문서에
회원 개인정보가 없으므로 이것은 받아들일 수 있는 선이다.
**단, 단가가 보인다** — 다른 지점 강사의 `fullRoomRate` 를 가린다면 그것은
규칙으로 못 하고(규칙은 필드를 숨기지 못한다) callable 이어야 한다.

## 4. 지점을 옮긴 회원 — 무엇을 기준으로 보는가

지금 코드에 **두 개의 지점**이 이미 따로 있다.

| | 어디 | 언제 정해지나 | 바뀌나 |
| --- | --- | --- | --- |
| **회원의 지금 지점** | `clients.locationId` | 등록할 때 | 바뀐다 (지금은 누구나) |
| **그 계약의 지점** | `passes.locationId` · `ledger.locationId` | **발급 순간에 박힌다** | 안 바뀐다 |

급여·매출은 이미 **박힌 쪽**으로 집계된다 (`payroll-repository.js:395` 가
`entry.locationId` 를 본다). 이것이 맞다 — 그 달의 매출은 그때 그 지점의 것이고,
회원이 나중에 옮겼다고 지난달 정산이 움직이면 안 된다.

### 제안하는 판정

| 무엇 | 기준 | 왜 |
| --- | --- | --- |
| 회원 목록 · 검색 · 등록 | **회원의 지금 지점** | 지금 누가 그 회원을 응대하는가의 문제다 |
| 회원권 처리 (취소·세션업·양도·만료일·잔여) | **그 회원권의 지점** | 그 계약이 어디 것인지로 정한다 |
| 급여 집계 · 발급 내역 | **원장 항목의 지점** | 이미 그렇다. 바꾸지 않는다 |
| 수업 기록 열람 | **그 수업의 지점** | |

**빈칸을 어떻게 읽는가:** `locationId` 가 없거나 `locations` 에 없는 값이면
**대표에게만 보인다.** "모르면 다 보여준다" 로 하면 경계가 없는 것과 같고,
"모르면 아무도 못 본다" 로 하면 회원이 조용히 사라진다. 대표 화면이 그 수를
세고, 0 이 되기 전에는 규칙을 켜지 않는다.

### 하나 남는 구멍 — 옛 지점의 회원권

회원이 반송점 → 율하점으로 옮기면 `clients.locationId` 는 율하점이 되지만,
반송점에서 산 회원권은 **반송점 그대로**다. 그러면 율하점 총괄매니저의 회원
목록에는 그 회원이 뜨는데, **그 회원권은 안 보인다.**

두 갈래다.

- **(가) 목록은 지금 지점, 회원권도 지금 지점** — 옛 지점 회원권은 안 보이고,
  처리는 대표나 옛 지점 총괄매니저가 한다. **규칙이 단순하다**
- **(나) 회원 상세는 "지금 지점 ∪ 그 회원 회원권의 지점"** — 보이기는 하는데,
  이 판정은 **질의로 표현할 수 없다** (회원권을 먼저 읽어야 안다). 규칙이
  복잡해지고, 틀렸을 때 아무도 모른다

**(가)를 권한다.** 대신 지점 이동 자체를 제대로 만든다 — 회원 지점 변경
callable(④)이 "이 회원의 살아 있는 회원권 N장도 함께 옮길까요?" 를 묻고,
옮기면 `passes.locationId` 를 함께 바꾼다. **원장은 건드리지 않는다**
(append-only — 지난 매출은 그때 그 지점의 것이다).

## 5. 규칙으로 할 것과 callable 로 할 것

**기준 하나:** 규칙은 **문서 하나를 보고 답할 수 있는 것**만 한다. 여러 문서를
읽어야 하거나, 읽기와 쓰기가 짝지어야 하거나, 되돌릴 수 없는 것은 callable 이다
(`pass-admin.js` · `instructor-swap.js` 머리말과 같은 판단).

| 권한 | 지금 | 총괄매니저 | 어디서 | 왜 |
| --- | --- | --- | --- | --- |
| 회원 목록·검색 | 규칙 | 규칙 (list + 질의) | **규칙** | 문서의 locationId 하나로 답한다 |
| 회원 등록 | 규칙 | 규칙 | **규칙** | `request.resource.data.locationId` 를 보면 된다 |
| 회원 지점 변경 | 규칙 (누구나) | **callable** | **callable** | ④ — 이것이 경계를 넘는 문이다 |
| 회원권 발급 | 규칙 | 규칙 | **규칙** | 회원권 문서의 locationId 로 답한다 |
| 발급 취소 | 대표만 | 맡은 지점 | **callable** | 회원권 + 원장 + 누적을 함께 되돌린다 |
| 세션업 | callable (`sessionUpPass`) | 맡은 지점 | **callable (있음)** | 지점 판정만 더한다 |
| 양도 | callable (`handoverPass`) | 맡은 지점 | **callable (있음)** | 양쪽 회원의 지점을 함께 본다 |
| 만료일 변경 | 규칙 (manager 가능) | 규칙 | **규칙** | 이미 한 필드짜리 문이 있다 (`:771`) |
| 잔여 조정 | 대표만 (규칙) | 맡은 지점 | **callable** | 원장 항목이 함께 가야 한다 |
| 담당 강사 변경 | 규칙 (manager, handedOver 동반) | 규칙 | **규칙** | 이미 그 모양이다 (`:756`) |
| 지점 급여 집계 | 대표만 (화면) | 맡은 지점 | **규칙 + 질의** | ledger 그룹 규칙에 지점 절을 더한다 |
| 수업 기록 열람 | 규칙 | 맡은 지점 | **규칙** | lessonNotes 에 지점 필드부터 |
| 강사 추가 | 규칙 (대표만) | 맡은 지점 | **callable** | 역할·지점 조합 검사가 규칙으로 안 된다 |
| 강사 퇴사 | 규칙 (대표만) | 맡은 지점 | **callable** | 같은 이유 |
| 강사 직급·단가 | 규칙 (대표만, rateHistory 동반) | 맡은 지점 | **callable** | 이력 + 감사 항목이 같은 배치여야 한다 |
| 강사 계정 교체 | callable (`swapInstructorAccount`) | 맡은 지점 | **callable (있음)** | 지점 판정만 더한다 |
| 상품 추가·보관 | 규칙 | 전 지점 공용 | **규칙** | ③-(가) |
| 총괄매니저 지정·해제 | — | **대표만** | **callable** | 자기 지점을 자기가 넓히는 길을 막는다 |
| 이관 초기화 | callable (대표만) | **불가** | 그대로 | |
| 앱 업데이트 설정 | callable (대표만) | **불가** | 그대로 | |

**"강사 추가가 왜 callable 인가":** 규칙이 `memberships` create 에서 막아야 할
것이 둘이다 — ⑴ 그 강사의 지점이 내 지점 안인가, ⑵ **역할이 나보다 낮은가**.
⑵ 를 규칙으로 쓰면 "owner 와 area_manager 가 아닌 것" 이라는 목록을 역할이 늘
때마다 고쳐야 하고, 하나 빠뜨리면 **총괄매니저가 총괄매니저를 만든다.** 서버에서
한 곳으로 묶는다.

### 반드시 규칙에도 남겨야 하는 것

callable 로 옮긴다고 규칙을 느슨하게 두면 안 된다. Admin SDK 가 규칙을
지나가는 것과, 규칙이 그 문을 열어 두는 것은 다르다. 위에서 callable 로 간
항목은 **규칙에서는 닫는다** — 지금 대표만 열려 있는 것은 대표만으로 둔다.

## 6. 묶을 것과 따로 낼 것

| 일 | 이번 묶음 | 왜 |
| --- | --- | --- |
| `instructorIds` 3단계 (강사는 담당 회원만) | **따로, 먼저** | 이미 끝나 있고 배포만 남았다. 지점 규칙과 섞으면 "빈 화면" 이 났을 때 둘 중 어느 쪽인지 못 가린다 |
| `lessonNotes` 강사 범위 축소 | **따로** (3단계와 함께) | 같은 경계(담당 회원)이고 같은 보류 조건을 쓴다 |
| `lessonNotes` 에 `locationId` 필드 추가 | **이번** | 지점 판정이 그 필드 없이는 불가능하다 |
| 변화기록 계열 8개 | **따로, 나중** | 8개를 한 번에 좁히는 일이고 총괄매니저와 무관하다 |
| 최소 빌드 규칙 (`RULES_MINIMUM_BUILD`) | **이번에 쓴다, 새로 만들지 않는다** | 아래 |
| 상품 진짜 수정·삭제 | **따로** | ③ |
| `memberships.locationIds` (복수) | **이번** | 총괄매니저가 여러 지점을 맡는다 = 이 필드가 곧 기능이다 |

**순서가 중요하다.** 3단계(담당 회원)와 지점 규칙은 **둘 다 "질의가 안 좁으면
화면이 통째로 빈다"** 는 같은 고장을 낸다. 같은 배포에 넣으면 고장 났을 때
되돌릴 단위가 하나다. **3단계를 먼저 켜고, 한 주 지켜본 뒤 지점을 켠다.**

## 7. 옛 앱이 막히는 경로

지점 규칙을 켜면 **좁히지 않은 질의를 보내는 모든 앱이 빈 화면을 본다.** 총괄매니저
한 사람의 문제가 아니다 — list 규칙에 `resource.data.locationId` 조건이 들어가는
순간, 그 조건을 증명하지 못하는 **모든 호출**이 거부된다.

| 빌드 | 보내는 질의 | 규칙 켠 뒤 |
| --- | --- | --- |
| ~1.1.33 / 65 (지금) | `clients` 조건 없음 | **회원 목록 전체가 빔** |
| ~1.1.33 / 65 | `passes` 조건 없음 | **회원권 전체가 빔** |
| 새 빌드 | `locationId in [...]` | 정상 |

**대표(owner)는 지점이 없다.** 규칙을 쓸 때 owner 절을 지점 조건 **밖에** 두면
대표 질의는 지금 그대로 통과한다 — 그래야 웹이 멈추지 않는다. 같은 이유로
`manager` 와 `instructor` 도 이번에는 건드리지 않는다. 지점 조건은
**`area_manager` 절에만** 붙인다.

> 그러면 "다른 지점은 안 보인다" 가 총괄매니저에게만 적용된다. FC매니저는
> 지시대로 지금 범위 그대로다.

### 막을 수 있는 장치가 이미 셋 있다

1. **`RULES_MINIMUM_BUILD`** (`src/App.jsx:546`, 지금 62) — 대표 화면이
   "강사 N명 모두 ○○ 이상입니다" 라고 말할 때만 규칙을 켠다. **같은 장치를
   그대로 쓴다.** 새 번호로 올린다
2. **`runtimeConfig/appUpdate` 필수 팝업** (#45) — 최소 빌드보다 낮으면
   [나중에] 가 없다. 규칙을 켜기 **전에** 이것부터 올린다
3. **`runtimeConfig/settlement` 최소 빌드** — 확정 자체를 막는다. 마지막 안전망

**순서:** ② 필수 팝업 → 강사 전원 갱신 확인 → ③ 확정 차단 → ① 규칙.
역순으로 하면 강사는 **고칠 자리에 있지 않은 고장**을 만난다.

## 8. 작업 크기 · 배포 순서 · 롤백

### 크기

| 덩어리 | 파일 | 크기 | 되돌릴 수 있나 |
| --- | --- | --- | --- |
| A. 역할 값 + 소속 `locationIds` + 지정 화면 | constants · rules · App.jsx · instructor-repository | 중 | 예 |
| B. 지점 점검 callable (읽기만) + 대표 화면 | functions · App.jsx | 소 | 예 (읽기만) |
| C. `locationId` 채우기 (clients · lessons · lessonNotes) | 트리거 · 백필 callable | 중 | 예 |
| D. 질의를 지점으로 좁히기 | repositories 6개 · 색인 3개 | 중 | 예 |
| E. 규칙 (list·get 에 지점 절) | rules | 소(줄 수) · **대(위험)** | **예 — 되돌리기 = 재배포** |
| F. callable 7개에 지점 판정 | functions | 중 | 예 |
| G. "총괄매니저 처리 내역" 화면 + 감사 항목 | rules(auditActions) · App.jsx | 중 | 예 |
| H. `ledger.locationId` 를 회원권과 대조 | rules | 소 | 예 |

**E 와 H 는 규칙 배포다.** 한 번 나가면 그 사이의 모든 쓰기에 적용된다.

### 배포 순서

```
0. 지점 점검 callable 배포 → 대표가 숫자를 본다          (읽기만, 위험 없음)
1. locationId 채우기 → 빈 것 0 이 될 때까지               (쓰기, 되돌릴 수 있음)
2. instructorIds 3단계 규칙 배포 → 한 주 지켜본다         ← 먼저, 따로
3. 역할 + 지정 화면 + 좁힌 질의가 담긴 앱 출시
4. appUpdate 필수 팝업 → 강사 전원 갱신 확인
5. settlement 최소 빌드
6. 지점 규칙 배포                                        ← 대표가 지시할 때만
7. 감사 기록 + 처리 내역 화면
```

**3 과 6 사이에 최소 한 번의 스토어 심사가 들어간다.** iOS 는 그 기간이
예측되지 않으므로, 그 사이에도 지금 앱이 정상으로 돌아야 한다 — 3번의 좁힌
질의는 **옛 규칙에서도 통과한다**(좁히는 것은 언제나 허용된다). 그래서 3 을
먼저 내도 안전하다.

### 롤백

| 단계 | 되돌리는 법 | 남는 것 |
| --- | --- | --- |
| 1 (채우기) | 되돌릴 필요 없음 — 값이 더 정확해질 뿐 | |
| 3 (앱) | 스토어는 되돌릴 수 없다. **runtimeConfig 로 끈다** | 좁힌 질의는 옛 규칙에서도 돈다 |
| 6 (규칙) | **직전 규칙 재배포** — `npm run test:rules` 통과본의 커밋 해시를 배포 직전에 적어 둔다 | 그 사이의 쓰기는 그대로 |
| 7 (감사) | append-only 라 안 지운다 | |

**6을 되돌릴 준비:** 되돌리기는 "고쳐서 다시" 가 아니라 **"그 해시를 그대로
다시"** 다 — 고장 난 상태에서 고친 규칙을 내보내는 것이 제일 위험하다.

### 화면이 지켜야 하는 것 넷

1. **지점 0개로 지정할 수 없다.** 0개면 아무것도 못 보는 역할이 되고, 그
   사람에게는 "권한이 없다" 와 구분되지 않는다
2. **대표 자신은 대상에서 뺀다.** `isDeputyDirector` 문이 자기 자신을 막는 것과
   같은 이유다 (`firestore.foundation.rules:1279`)
3. **지정 전에 그 사람이 지금 무엇인지 보여준다.** 강사였다면 담당 회원이 있고,
   총괄매니저가 되어도 그 담당은 그대로다 — 급여도 그대로다
4. **해제는 "강사로 되돌리기" 다.** 퇴사가 아니다. 계정 교체 화면이
   "퇴사가 아닙니다" 를 먼저 말하는 것과 같은 자리다

### 처리 내역 화면

**자리:** 더보기 → 센터 운영 → **[총괄매니저 처리 내역]**. 감사 로그와 나란히
두되 따로 둔다 — 감사 로그는 "이상한 건" 을 모으고, 이쪽은 "누가 무엇을
했는가" 를 시간순으로 본다.

```
지점 v  사람 v  2026-10 v
──────────────────────────────
10/09 14:22  반송점 · 정예진
  잔여 조정    회원 OOO    8회 → 10회
10/09 11:05  율하점 · 정예진
  발급 취소    회원 OOO    1:1 20회 · 1,300,000원
```

### 감사 항목 — 규칙을 고쳐야 한다

`auditActions()` 가 닫힌 목록이고 (`firestore.foundation.rules:1517`),
`mayRecordAudit` 이 **대표만** 허용한다 (`:1530`). 둘 다 바꿔야 총괄매니저의
조작이 기록된다.

더할 항목: `remaining_adjusted` · `pass_cancelled` · `pass_price_override` ·
`instructor_rate_set` · `instructor_title_set` · `instructor_revoked` ·
`instructor_swapped` · `product_changed` · `area_manager_set` ·
`area_manager_cleared`

필드도 모자란다. 지금 `hasOnly` 에 **전/후 값을 담을 칸이 `amount` ·
`previousAmount` 둘뿐**이다 (`:1552`). 잔여 조정(회차)과 발급 취소(금액)가
같은 칸을 쓰면 화면이 무엇인지 모른다 → `previousCount` · `newCount` ·
`passId` 를 더한다.

> **자유 문장 칸은 절대 더하지 않는다.** 규칙 주석이 이유를 적어 두었다 —
> "있으면 언젠가 거기에 회원 이름이 들어간다" (`:1550`). 처리 내역의 회원
> 이름은 `clientId` 로 적고 화면이 명부에서 찾는다.

**한 가지 더:** callable 로 처리하는 것들(잔여 조정·발급 취소·강사 단가 등)은
**Admin SDK 가 감사 항목을 쓴다.** 그러면 `mayRecordAudit` 을 총괄매니저에게
열 필요가 없다 — 규칙은 대표만으로 두고, 기록은 서버가 남긴다. **이쪽이
안전하다**: 앱에서 감사 항목을 쓸 수 있으면 하지 않은 일의 기록을 지어낼 수
있고, 규칙 주석이 바로 그것을 막고 있다 (`:1526`).

## 내가 확정하지 못한 것 — 대표가 답해야 한다

1. **역할 이름** — `area_manager` 로 가도 되는가 (①). `branch_manager` 는 이미
   점장 직함이고 급여 규칙이 그것을 본다
2. **상품 수정·삭제** — ③-(가) 추가·보관만으로 가도 되는가
3. **다른 지점 강사의 단가가 보여도 되는가** (3-3). 가리려면 강사 목록이
   callable 이 되고 작업이 한 덩어리 늘어난다
4. **지점 이동 회원** — 4번의 (가), 즉 "회원권도 함께 옮기는 callable" 로 가도
   되는가
5. **총괄매니저도 "확인할 수업" 큐를 보는가** — 적어 주신 목록에 없었다.
   맡은 지점의 미확정 수업을 대신 확정할 수 있어야 하는지

## 한 줄 요약

**역할 하나를 더하는 일이 아니다.** 지금 이 센터는 지점이라는 경계를 서버 어디에도
가지고 있지 않고(1번), 목록은 전부 통째로 내려받아 기기에서 거른다(②). 총괄매니저는
그 경계를 **처음 만드는** 일이고, 경계가 생기는 순간 지점 값 자체가 문이 된다(④).

그래서 작업의 대부분은 역할이 아니라 **locationId 를 믿을 수 있게 만드는 것**이다 —
비어 있는 것을 채우고(2), 질의를 좁히고(3), 아무나 못 바꾸게 잠그고(④),
원장과 대조하고(2-2).

**0번(점검 callable)부터 시작하기를 권한다.** 숫자를 보기 전에는 1번이 하루인지
한 주인지 아무도 모른다.
