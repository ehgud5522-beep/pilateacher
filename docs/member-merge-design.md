# 회원 합치기 — 설계 (구현 전)

**아직 만들지 않았다.** 연락처 수정(2026-09-25)을 하면서 "같은 사람이 회원
둘로 생긴 경우" 가 남았고, 이 문서는 그것을 어떻게 풀지 적어 둔 것이다.

---

## 1. 왜 생기나

번호가 회원의 정체이기 때문이다. 같은 사람이 둘이 되는 길은 넷이었다.

| 길 | 지금은 |
| --- | --- |
| 엑셀에 번호를 잘못 적어 올림 | 그대로 남아 있다 |
| 앱 등록에서 번호를 잘못 침 | 그대로 남아 있다 |
| 번호를 바꾼 뒤 새 번호 엑셀을 다시 올림 | **막았다** (phone 으로 먼저 찾는다) |
| 번호를 바꾸기 전 엑셀을 나중에 올림 | **막았다** (`previousPhones`) |

앞의 둘은 사람이 잘못 친 것이라 프로그램이 막을 수 없다. 그래서 합치기가
필요하다.

## 2. 무엇을 합치나 — 회원 문서 둘, 그 아래 전부

| 옮길 것 | 어디에 | 어려움 |
| --- | --- | --- |
| 회원권 `passes` | `clientId` · `clientIds` 가 지운 쪽을 가리킴 | **규칙이 둘 다 immutable** |
| 원장 `passes/*/ledger` | 항목의 `clientId` | **append-only — 고칠 수 없다** |
| 강사 누적 `instructorClientTotals` | 문서 id 가 `{강사}_{회원}` | 두 문서를 더해야 함 |
| 수업 참석 `lessons/*/participants` | 문서 id 가 `clientId` | update·delete 가 막혀 있음 |
| 회원 앱 연결 `memberLinks` · `clients.userId` | 둘 중 하나만 연결돼 있을 수 있음 | 서버만 씀 |
| 투영 `memberViews` | 문서 id 가 `clientId` | 트리거가 다시 만듦 |
| 수업기록 `lessonNotes` | 문서 id 가 `{lessonId}_{clientId}` | `clientId` immutable |
| 기기 명부 | 강사 폰마다 따로 | 서버가 못 건드림 |

**원장이 결정적이다.** append-only 라 이미 쌓인 항목의 `clientId` 를 고칠 수
없고, 고칠 수 있게 여는 순간 급여의 근거가 사후에 움직일 수 있게 된다 --
그것만은 열 수 없다.

## 3. 그래서 "합치기" 가 아니라 "잇기" 다

원장을 옮기는 대신 **두 회원 문서를 하나로 가리키게** 한다.

```
clients/csv_01012345678   (남길 쪽, primary)
clients/csv_01099998888   { mergedInto: "csv_01012345678", status: "merged" }
```

- 지운 쪽은 **지우지 않는다.** 원장이 그 id 를 가리키고 있고, 지우면 그
  회차들이 누구 것인지 영영 알 수 없다.
- 읽는 쪽이 `mergedInto` 를 따라간다. 잔여·이력·여정은 두 문서를 합쳐 센다.
- 급여는 건드리지 않는다. 원장 항목은 그대로이고 `instructorId` 도 그대로라,
  **합치기 전후로 급여 합계가 한 푼도 달라지지 않는다.** 이것이 이 설계를
  고르는 가장 큰 이유다.

## 4. 그래도 손대야 하는 것

| 무엇 | 왜 |
| --- | --- |
| `instructorClientTotals` | 판정 3(이 강사에게 20회 미만)이 이 숫자를 본다. 갈라져 있으면 같은 회원인데 신규 단가를 두 번 탄다. **더해서 primary 쪽에 쓰고, 지운 쪽은 0 으로.** |
| `memberLinks` · `userId` | 회원 앱은 한 사람에게 하나여야 한다. 지운 쪽 연결을 끊고 primary 로 다시 잇는다. |
| `previousPhones` | 지운 쪽의 번호를 primary 의 `previousPhones` 에 넣는다 -- 그래야 옛 엑셀이 다시 그 회원을 만들지 않는다. |

## 5. 읽는 쪽이 따라가야 하는 곳

`mergedInto` 를 따라가지 않으면 합쳐지지 않은 것과 같다.

- `listPasses(clientId)` — primary 로 물으면 지운 쪽 회원권도 나와야 함
- `loadClientPassHistory` — 원장 둘을 합쳐 시간순
- `member-view-triggers` 의 `collectMemberViewInput` — 투영을 primary 하나로
- `roster-visibility` 의 `isMyClient` — 지운 쪽 회원권도 내 회원
- 급여 집계 — **건드리지 않는다.** 원장을 그대로 세므로 저절로 맞는다

## 6. 화면

대표 전용. 회원 상세에 [회원 합치기] → 남길 쪽을 고르고 → 무엇이 합쳐지는지
(회원권 N개·수업 N회·누적 N회) 보여 준 뒤 확인.

**되돌리기는 만들지 않는다.** `mergedInto` 를 지우면 되긴 하지만, 그 사이에
쌓인 원장이 어느 쪽에 붙었는지가 갈라진다. 대신 **누르기 전에 무엇이 합쳐지는지
전부 보여 준다** -- 양도와 같은 원칙이다.

## 7. 왜 지금 안 만드나

1. **먼저 세어 봐야 한다.** 실제로 몇 건인지 모른다. 번호 철자가 깨진 회원
   목록(`listMalformedClientPhones`)을 대표가 정리한 뒤에야 "같은 사람이 둘"
   이 몇 명인지 드러난다.
2. 한 건이나 두 건이면 **손으로 정리하는 편이 싸다** -- 회원권을 취소하고 다시
   발급하는 길이 이미 있다. 열 건이 넘으면 이 기능을 만든다.
3. 읽는 쪽 다섯 곳을 전부 고쳐야 하고, 한 곳이라도 빠지면 그 화면만 조용히
   반쪽을 보여준다. 양도보다 무겁다.

## 8. 그때 지킬 것

- 원장은 끝까지 append-only 다. 항목의 `clientId` 를 고치지 않는다
- 지운 쪽 문서를 지우지 않는다
- 합치기 전후로 급여 합계가 달라지지 않는지 **테스트로 고정**한다
- 대표만, 감사에 남긴다 (누가·언제·어느 둘을)
