# 서버 기준 동기화 설계 — 같은 계정이면 PC · 폰 어디서나 같은 데이터

2026-10-31 초안, 같은 날 대표 결정 반영. **[결정]** 은 아직 정하지 않은 것이다.

## 최종 목표

같은 계정으로 PC 웹 · 폰 앱 어디서 로그인해도 회원 · 일정 · 출석 · 수업기록 · 메모가
같게 보인다. 서버의 문서가 기준이고, 기기의 데이터는 그 캐시다.

**범위 밖 (제외):** 사진. 용량 때문에 동기화하지 않는다. 원본은 기기에만 둔다
(2026-10-31 대표). 이미 올라간 사진 백업(`photoBackups` · Storage `users/{uid}/photos`)은
지금처럼 새 기기 복원용으로만 남는다.

**범위 밖 (보류):** 센터에 소속되지 않은 강사 계정. 회원부터 전부 기기에만 있고 구조가
센터와 달라 따로 설계해야 한다. 이번 목표에서 뺀다 (2026-10-31 대표).

| 데이터 | 서버 | 기기에만 |
| --- | --- | --- |

| 회원에게 보낸 한마디 (`lessonNotes`) | 기준 | |
| 예정 · 확정 수업 (`lessons`) | 올리기만 (3단계) | 기기 일정이 원본 |
| 일정 전체 · 개인 일정 · 강사 메모 | | ✓ |
| 출석 | | ✓ |
| 수업기록 (AI) | | ✓ |
| 회원별 메모 · 목표 | | ✓ |
| 사진 | 한 장씩 올라가 있음 (`photoBackups`) | 다른 기기로 내려오지 않음 |

기기 → 서버는 `lessons` 하나뿐이고, 서버 → 강사 앱은 없다 (`listLessonsByRange` 는
"Not implemented"). 그래서 **PC 웹에서 넣은 일정은 강사 폰 앱에 보이지 않는다.**

백업 (`users/{uid}/backup/latest`):

- 기기마다 자기 db **전체를 문서 하나에** 올린다. 내려받는 것은 빈 기기일 때뿐이다.
- **같은 계정의 두 기기가 이 한 자리를 번갈아 덮는다.** 복원하면 다른 기기 것은 빠진다.
- 문서 하나의 한도는 1 MiB 다. 수업기록이 쌓이면 백업 자체가 실패할 수 있는데, 크기를
  미리 보는 장치가 없다.

함께 드러난 것:

1. 확정 되돌리기(`correctDeduction`)가 서버 수업 문서를 건드리지 않는다. 되돌린 뒤에도
   "completed" 라서, 그 수업은 다시는 회원 앱에 나가지 않는다.
2. 확정(`deductPass`)은 수업 문서를 merge 없이 set 한다. 회원권 둘을 차감하는 듀엣은 두
   번째가 첫 번째를 덮어 서버에 한 사람만 남는다 (3단계 전부터).
3. 최소 버전 장치(`settlement-gate.js`)는 설정을 못 읽으면 열어 둔다. 옛 빌드에는 이
   장치 자체가 없다 -- 화면 장치만으로는 옛 빌드를 막지 못한다.

## 0단계 — 백업 안전망

1. **기기별 자리.** `users/{uid}/backup/device_{기기 id}`. 기기 id 는 처음 실행 때 만들어
   기기에 둔다. `latest` 는 당분간 같이 쓴다 (옛 빌드가 복원을 그 자리에서 찾는다).
   복원은 자리 목록을 보여 주고 고르게 한다 (기기 종류 · 마지막 백업 시각 · 개수).
   규칙은 이미 `backup/{backupId}` 아무 이름이나 본인에게 연다 -- 고칠 것이 없다.
   백업 문서에 앱 빌드 번호를 남긴다 (아래 "기기 목록" 이 이것을 쓴다).
   덮어쓰기 보호는 **자기 지난 백업과** 견준다. latest 와 견주면 PC(40건) 뒤 폰(3건)이
   매번 막힌다. latest 는 다른 기기의 더 큰 백업을 줄여 덮지 않는다 (#101).
2. **크기 경고.** 올리기 전에 직렬화한 크기를 잰다. 800 KiB 를 넘으면 진단과 화면 경고,
   1 MiB 를 넘으면 올리지 않고 `backup/too-large` 로 남긴다 (지금은 Firestore 가
   `invalid-argument` 로 거절하고 원인이 뭉개진다).
3. **옮기기 전 스냅샷.** `users/{uid}/snapshots/{기기 id}_{시각}/db.json` (Storage).
   본인만 읽고 만든다. **고치기 · 지우기 없음.** 크기 한도 20 MiB, `application/json`.
   **사진 원본은 넣지 않는다** -- 사진 목록(어느 회원의 어느 사진, 기기 blobId · 클라우드 경로)
   까지만 담는다 (대표). 0단계에서는 자리와 "지금 스냅샷 남기기" 만 만든다. 자동으로 찍는 것은 각 데이터를
   서버로 옮기기 직전이다.

## 1단계 — 동기화 틀

### 공통 칸

동기화하는 모든 문서에:

- `revision` (정수, 쓸 때마다 +1) · `updatedAt` · `updatedBy` · `updatedDevice`
- `deletedAt` -- 지우지 않고 표시한다 (아래 "삭제")

### 보내기 · 받기

- 보내기: 트랜잭션 안에서 서버 revision 을 읽고, 기기가 마지막으로 본 revision 과 같을 때만
  +1 해서 쓴다.
- 받기: 열 때 · 30초 넘게 떠났다 돌아올 때 · 저장 직후. 데이터 종류마다 `updatedAt` 커서로
  바뀐 것만 읽는다. 실시간 리스너를 쓸지는 이 단계에서 정한다 (Firestore 오프라인 캐시 포함).
- 기기 db 는 서버의 캐시다. 화면은 지금처럼 기기 db 를 그린다 -- 30,000 줄 화면을 한 번에
  서버 읽기로 바꾸지 않는다. 받은 것을 기기 db 에 합치는 층이 틀의 한가운데다.

### 같은 것을 두 기기에서 고쳤을 때

**낙관적 잠금 + 서버가 이긴다 + 밀린 수정은 버리지 않는다.**

- revision 이 다르면 (그사이 다른 기기가 고쳤다) 쓰지 않는다. 서버 것으로 기기를 맞추고
  "다른 기기에서 먼저 고친 내용이라 그것으로 맞췄어요. [내 수정 다시 적용]".
- 삭제 대 수정 → 먼저 저장한 쪽이 이긴다. 진 쪽에는 "다시 살리기" 를 준다.
- 확정 대 수정 · 삭제 → 확정이 언제나 이긴다 (4단계 잠금 문구).
- 오프라인에서 고친 것은 큐에 마지막 revision 과 함께 남고, 연결되면 같은 판정을 지난다.

### 삭제

`deletedAt` 표시로 지운다. 30일 동안 남긴다. 오래 꺼져 있던 기기가 켜져도 지운 것을
되살리거나, 다른 기기가 새로 만든 것을 지우지 못하게 하기 위해서다.

### 기기 목록

`users/{uid}/devices/{기기 id}` -- 기기 종류 · 앱 빌드 · 마지막으로 본 시각. 0단계의 기기별
백업과 같은 기기 id 를 쓴다. 전환 스위치가 이것을 본다.

### 전환 스위치

데이터 종류별 · 계정별로 "서버가 기준" 을 켠다. 켜는 순서: **대표 계정 → 강사 한 명 → 전체.**

**켤 수 있는 조건 (모두):**

1. 필라티처 Android 프로덕션이 그 기능을 담은 빌드로 **100% 출시** 됐다.
2. **최소 버전 강제** 가 걸렸다 -- 새 빌드는 최소보다 낮으면 동기화 데이터를 쓰지 못하고
   업데이트 화면을 띄운다. 이 장치는 설정을 못 읽으면 **닫는다** (확정 게이트와 반대다.
   여기서 열어 두면 옛 기기의 수정이 조용히 사라진다).
3. 그 계정의 기기 목록에서 최근 30일 안에 본 기기가 전부 최소 버전 이상이다. iOS 기기도
   여기서 함께 센다.

옛 빌드는 이 장치를 갖고 있지 않으므로 3번이 실제 차단이다 -- 옛 빌드가 남은 계정은 켜지
않는다. 스위치는 끌 수 있다. 끄면 기기가 다시 원본이 되고, 서버에 쓴 것은 그대로 남는다.

## 2단계 — 일정 (틀의 첫 대상)

### 서버에 두는 것

| 칸 | 어디에 | 비고 |
| --- | --- | --- |
| 날짜 · 시각 · 센터 회원 id · 강사 uid · 지점 | `lessons` (지금 그대로) | |
| 수업 종류 · 기구 · 방 | `lessons` 에 추가 | 센터 직원이 봐도 되는 정보. 회원 데이터에는 싣지 않는다 (허용 목록) |
| 공통 칸 (revision …) | `lessons` | |
| 강사 메모 · 상담 · 휴무 | 3단계에서 본인 전용 자리로 | 그 전까지는 기기에만 |
| 출석 | 4단계에서 | 그 전까지는 "출석과 확정은 같은 기기에서" |

### 읽어서 합치기

읽는 것: `lessons` 중 `instructorId == 나`, 오늘 -7일 ~ +60일 (색인 1개: instructorId +
startsAt). 일정 id 가 같으면 같은 수업이다.

| 서버 | 기기 | 하는 일 |
| --- | --- | --- |
| scheduled | 없음 | 더한다. 센터 회원 id → 명부의 기기 회원. 명부에 없으면 진단 |
| scheduled | 서버 revision 이 더 큼 | 핵심 칸을 서버 것으로. 메모 · 출석은 기기 것을 지킨다 |
| cancelled | 있음 | 지운다. 기기에 출석으로 뺀 회차가 있으면 지우지 않고 진단 |
| completed | 있음, 기기는 미확정 | 잠근다 ("다른 기기에서 확정됨") |
| completed | 없음 | 더하지 않는다 |

같은 강사 · 같은 시작 시각 · 같은 회원인데 id 가 다른 쌍은 "중복 의심" 으로 보여 주고
고르게 한다. **자동으로 지우지 않는다.**

### 함께 고칠 것

- 확정 되돌리기 → 서버 수업 status 를 scheduled 로 돌린다.
- 확정은 merge 로 쓴다.

### 규칙

- `lessons` update: `revision == resource.revision + 1` (없던 옛 문서는 1 로 시작).
- completed 는 일정 쓰기로 scheduled · cancelled 가 되지 못한다. 확정 되돌리기만 돌린다.

진단: `schedule_sync_conflict` (stage: save · pull, lessonId, serverRevision,
deviceRevision, winner). 이름 · 메모는 남기지 않는다.

## 5단계 — 수업기록 열람 (기본안, 그 단계 전에 다시 정한다)

- 열람: **작성한 강사와 대표.** FC매니저는 기본 비공개.
- 담당이 바뀌면 새 담당은 이전 기록을 **읽기 전용** 으로 본다.
- 수정은 **작성자만.**

## 기기 데이터를 서버로 옮길 때

1. **옮기지 않고 복사한다.** 기기 데이터는 지우지 않는다. 서버 사본을 확인한 뒤에야
   스위치를 켠다.
2. **직전 스냅샷.** 0단계의 스냅샷 자리에 자동으로 찍는다. 무엇이 꼬여도 이것으로 돌아간다.
3. **id 를 그대로.** 기기의 id 를 문서 id 로 쓴다. 끊겨서 다시 돌려도 같은 문서에 쓰일 뿐
   두 벌이 생기지 않는다. 몇백 건씩 나눠 쓰고, 어디까지 했는지 기기에 적어 이어 간다.
4. **두 기기는 덮지 않고 합친다.** 먼저 옮긴 기기가 기준이다. 같은 id 인데 내용이 다르면 두
   판을 남겨 고르게 한다. id 가 다르고 같은 회원 · 같은 시각이면 "중복 의심".
5. **먼저 계획을 보여 준다.** "일정 120 · 수업기록 340 을 올립니다" → 확인 → 실행 → 서버를
   다시 읽어 개수 대조. 결과는 진단에 개수만 남긴다.
6. **옛 빌드를 막는다.** 위 전환 스위치 조건.
