# 5단계 설계 — 서버의 일정을 강사 앱이 읽어 기기에 합치기

2026-10-31 초안. 대표 결정이 필요한 곳은 **[결정]** 으로 표시했다.

## 지금 (확인한 사실)

| 방향 | 있나 | 어디 |
| --- | --- | --- |
| 기기 → 서버 `lessons` | 있다 (3단계) | `schedule-publish.js` · `lesson-schedule-repository.js` |
| 서버 `lessons` → 강사 앱 일정 | **없다** | `listLessonsByRange` 는 "Not implemented". 서버 lessons 를 읽는 곳은 대표 회원 상세의 "센터 수업 기록" 하나뿐 |
| 기기 전체 → 클라우드 백업 | 있다 | `fbPushBackup` -- 기기마다 자기 db 전체를 올린다 |
| 클라우드 백업 → 기기 | 빈 기기일 때만 | 새 폰 복원. 쓰던 기기에는 내려오지 않는다 |

그래서 **PC 웹에서 넣은 일정은 강사 폰 앱에 보이지 않는다.** 두 기기는 각자의 일정을
들고, 서버로 올리기만 한다.

함께 드러난 것:

1. **같은 계정의 두 기기가 같은 백업 한 자리를 번갈아 덮는다.** PC 가 저장하면 PC 의 db 가,
   폰이 저장하면 폰의 db 가 백업이 된다. 그 백업으로 복원하면 다른 기기 것은 빠진다.
   5단계와 별개로 알고 있어야 한다.
2. **확정 되돌리기(`correctDeduction`)가 서버 수업 문서를 건드리지 않는다.** 되돌린 뒤에도
   서버에서는 "completed" 이고, 일정 쪽은 완료를 덮지 않으므로 그 수업은 다시는 회원 앱에
   나가지 않는다. 5단계에서 함께 고친다.
3. 확정(`deductPass`)은 수업 문서를 **merge 없이 set** 한다. 회원권 두 개를 차감하는
   듀엣은 두 번째가 첫 번째를 덮어 서버에 한 사람만 남는다 (3단계 전부터).

## 원칙

- **예정 일정은 서버가 기준이다.** 기기는 서버의 사본에 자기 것을 더한 것이다.
- **확정된 수업은 어느 쪽도 덮지 않는다.** 일정 쓰기는 completed 를 건너뛰고(이미 그렇다),
  내려받기도 기기의 확정 기록을 지우지 않는다. 규칙으로도 막는다(아래).
- 사용자가 만든 것은 버리지 않는다 (CLAUDE.md 5). 충돌로 밀린 수정은 버리지 않고 다시
  적용할 수 있게 남긴다.
- 실시간 리스너는 쓰지 않는다. 회원 앱과 같이 **열 때 · 30초 넘게 떠났다 돌아올 때 ·
  저장 직후** 에 읽는다 (대표 결정 "즉시 = 열거나 돌아올 때").

## 무엇을 서버에 두나

지금 `lessons` 문서는 회원 데이터의 재료만 들고 있다 (날짜 · 시각 · 유형 · 강사 uid ·
지점 · 센터 회원 id). 강사 앱이 그것만으로 일정을 다시 그리려면 모자라다.

| 칸 | 어디에 | 이유 |
| --- | --- | --- |
| 날짜 · 시각 · 센터 회원 id · 강사 uid · 지점 | `lessons` (지금 그대로) | |
| 수업 종류 (개인레슨 · 듀엣 · 그룹), 기구, 방 | `lessons` 에 추가 | 센터 직원이 봐도 되는 정보. 회원 데이터에는 여전히 싣지 않는다 (허용 목록) |
| `revision` · `updatedAt` · `updatedBy` · `updatedDevice` | `lessons` 에 추가 | 충돌 판정 (아래) |
| 강사 메모 | **[결정]** 기기에만 / `users/{uid}/lessonMemos/{id}` (본인만) | 3단계에서 메모는 `lessons`(센터 직원 누구나 읽는다)에 싣지 않기로 했다. 기기 간에 보려면 본인 전용 자리가 필요하다 |
| 상담 · 휴무 같은 개인 일정 | **[결정]** 기기에만 / `users/{uid}/personalEvents/{id}` (본인만) | 지금은 서버에 아예 안 간다. 폰에서 보려면 필요하다 |
| 출석 상태 (출석 · 노쇼 · 취소) | **[결정]** 기기에만 / `lessons` 의 participants | 출석을 폰에서 찍고 확정을 PC 에서 하려면 서버에 있어야 한다 |

권장: 메모 · 개인 일정은 본인 전용 자리로, 출석은 이번에는 기기에 두고 "출석과 확정은
같은 기기에서" 로 시작한다. 출석까지 옮기면 확정 경로 전체가 바뀐다.

## 읽어서 합치기

읽는 것: `lessons` 중 `instructorId == 나`, 날짜가 오늘 -7일 ~ +60일.
(복합 색인 1개 필요: instructorId + startsAt)

일정 id 가 같으면 같은 수업이다. 서버 문서마다:

| 서버 | 기기 | 하는 일 |
| --- | --- | --- |
| scheduled | 없음 | 기기에 더한다. 센터 회원 id → 명부의 기기 회원으로 잇는다. 명부에 없으면 "명부에 없는 회원" 으로 두고 진단을 남긴다 |
| scheduled | 있음, 기기 revision < 서버 | 핵심 칸(날짜 · 시각 · 종류 · 회원 · 기구 · 방)을 서버 것으로. 메모 · 출석은 기기 것을 지킨다 |
| scheduled | 있음, 같은 revision | 아무것도 안 한다 |
| cancelled | 있음 | 기기에서 지운다. 단 기기에 출석으로 뺀 회차(`deductFrom`)가 있으면 지우지 않고 진단을 남긴다 |
| completed | 있음, 기기는 미확정 | 기기 일정을 잠근다 ("다른 기기에서 확정됨"). 차감 내역은 원장에 있다 |
| completed | 없음 | 더하지 않는다 (지난 수업은 원장 · 회원 상세가 보여준다) |

기기에만 있고 서버에 없는 예정 일정은 지금처럼 올린다 (처음 맞추기).

## 같은 일정을 두 기기에서 고쳤을 때

**낙관적 잠금 + 서버가 이긴다 + 밀린 수정은 다시 적용 버튼으로.**

1. 모든 `lessons` 문서에 `revision` (정수). 일정 쓰기는 트랜잭션 안에서 읽은
   revision 에 1 을 더해 쓴다. 기기 일정은 마지막으로 본 `serverRevision` 을 든다.
2. 저장할 때 트랜잭션이 서버 revision 과 기기의 `serverRevision` 을 견준다.
   - 같다 → 쓴다. 기기의 `serverRevision` 을 새 값으로.
   - 다르다 (그사이 다른 기기가 고쳤다) → **쓰지 않는다.** 서버 것으로 기기를 맞추고,
     내가 하려던 수정은 버리지 않고 들고 있는다.
     토스트: "다른 기기에서 먼저 고친 일정이라 그 내용으로 맞췄어요. [내 수정 다시 적용]"
     누르면 서버 최신 위에 내 수정을 다시 얹어 새 revision 으로 쓴다.
3. 경우별:
   - 둘 다 시간을 고침 → 먼저 저장한 쪽이 서버에 남고, 나중 쪽은 위 토스트.
   - 한쪽은 삭제, 한쪽은 수정 → 먼저 저장한 쪽이 이긴다. 삭제가 먼저면 수정한 기기에서
     일정이 사라지고 "다시 살리기" 를 준다. 수정이 먼저면 삭제한 기기에 일정이 돌아온다.
   - 한쪽이 확정 → 확정이 언제나 이긴다. 다른 기기의 수정 · 삭제는 쓰이지 않고
     잠금 문구가 나온다 (4단계 문구와 같다).
4. 오프라인에서 고친 것은 큐에 `serverRevision` 과 함께 남고, 연결되면 같은 판정을 지난다.
5. 같은 수업을 폰에서 손으로 다시 넣은 경우 (id 가 다르다): 처음 합칠 때 같은 강사 ·
   같은 시작 시각 · 같은 회원인 쌍을 "중복 의심" 으로 보여 주고 고르게 한다.
   **자동으로 지우지 않는다.**

진단: `schedule_sync_conflict` (stage: save · pull, lessonId, serverRevision,
deviceRevision, winner). 이름 · 메모는 남기지 않는다.

## 규칙

- `lessons` update: `request.resource.data.revision == resource.data.revision + 1`
  (revision 이 없던 옛 문서는 1 로 시작). 옛 버전 앱이 revision 없이 덮는 것을 서버가 막는다.
- completed 문서는 일정 쓰기로 scheduled · cancelled 가 되지 못한다. 되돌릴 수 있는 길은
  확정 되돌리기(대표) 하나 -- 그때 status 를 scheduled 로 돌린다 (위 "드러난 것 2").
- 확정은 merge 로 바꾼다 (위 "드러난 것 3").
- 규칙 테스트는 #99 처럼 **앱 함수를 그대로** 에뮬레이터에 통과시킨다. 충돌 경로
  (두 기기 · 삭제 대 수정 · 확정 대 수정)를 각각 하나씩.

## 순서 제안

1. 규칙 + 쓰기 쪽 revision (기존 앱은 그대로 동작해야 한다)
2. 읽어서 합치기 (PC 웹부터)
3. 충돌 토스트 · 다시 적용 · 중복 의심
4. 확정 되돌리기 → status 복귀, 확정 merge
5. 메모 · 개인 일정 (결정에 따라)
6. 강사 폰 앱 출시 (3 · 4 · 5단계 함께)

**강사 폰 앱 새 버전 출시는 5단계가 끝날 때까지 보류한다** (2026-10-31 대표).

## 결정이 필요한 것

1. 강사 메모를 기기 간에 볼 것인가 (본인 전용 서버 자리)
2. 상담 · 휴무 같은 개인 일정을 기기 간에 볼 것인가
3. 출석을 서버에 둘 것인가, 이번에는 "출석과 확정은 같은 기기에서" 로 갈 것인가
4. 대표가 다른 강사의 일정을 넣는 경우도 이번에 포함하는가 (그 강사의 폰에 보이게)
